# Куда движется проект: фронт, бэк, своя ВМ

Записка для коллеги, который будет писать бэкенд на Go, и памятка себе.
Про сегодняшний код — [DEV.md](../DEV.md), про запуск — [README.md](../README.md).

## 0. Что решили

- **Фронт** — React + TypeScript + Vite, переносим экран за экраном, поле последним.
- **Репозитории** — два в организации `ghost-five`: `frontend` и `backend`. Заведены.
- **Хостинг** — своя ВМ, своё всё: Postgres, аккаунты, письма через SMTP Яндекса.
  Supabase выключаем, когда переезд закончится.
- **Первым делом** — золотые тесты движка. Сделано: `fixtures/` и
  `node tools/fixtures-check.mjs`, 25 случаев.

Разделы ниже объясняют, почему так и что из этого следует.

## 1. Где мы сейчас, если честно

Бэкенда у нас **нет**. Браузер ходит в Supabase напрямую:

- аккаунты и письма — Supabase Auth;
- данные — Postgres, доступ ограничен правилами RLS;
- «живость» — Realtime-подписки Supabase;
- **правила партии считает клиент**: игрок сам пишет новое состояние в `games.state`,
  а честность держится на том, что оба игрока считают одно и то же и что RLS не даёт
  писать в чужую партию. Рейтинг — единственное, что считает сервер (функция
  `report_result`), именно потому, что его подделали бы первым.

Отсюда главный вывод: «разделить проект на фронт и бэк» — это не перекладывание
папок. Бэк придётся **написать**, а вместе с ним решить, что делать с аккаунтами,
письмами и соединением в реальном времени, которые сейчас бесплатно даёт Supabase.

Хорошая новость: правила уже живут в чистом виде (`engine.js` — функции над JSON,
ни DOM, ни сети), поэтому их можно без переделки запустить на сервере.

## 2. Целевая картина

```
браузер (React)  ──HTTP──►  api (лобби, аккаунты, история, рейтинг)
      │                        │
      └───────WebSocket───────►│  партия: ходы, раскрытие, часы
                               ▼
                           Postgres
```

Ключевое изменение смысла: **источник истины переезжает на сервер**. Сервер держит
состояние партии, применяет ход правилами и рассылает результат. Клиент рисует и
подсказывает, но не решает.

Что из этого следует:

- тайный ход упрощается. Сейчас мы прячем ход хешем, потому что соперник физически
  видит базу. Серверу можно просто не отдавать чужой ход, пока не сходили оба, —
  commit-reveal и соль становятся не нужны;
- часы становятся серверными: «не успел» определяет сервер, а не вкладка;
- жульничество через консоль браузера перестаёт работать;
- появляется место для античита, лимитов и логов.

## 3. Фронт: React или нет

**Рекомендую React + TypeScript + Vite.** Не потому, что ванильный код плох — он
работает и быстрый, — а потому что:

- в команде двое, и React — общий язык, который не надо объяснять;
- типы из общего пакета `protocol` будут проверяться прямо в компонентах;
- экраны (лобби, друзья, профиль, лидеры, история) — это ровно те формы и списки,
  где React экономит время; сейчас они написаны вручную через `innerHTML`.

Честные минусы: поле 13×13 с анимациями сегодня перерисовывается точечно и стоит
дёшево; на React за этим придётся следить (`memo`, ключи, отдельный компонент
клетки). Это решаемо, но это работа.

Порядок переноса, чтобы не встать на месяц:

1. `packages/engine` — текущий `engine.js` как есть, затем типизировать;
2. каркас на Vite + роутер, общий макет и тема (CSS-переменные переносятся без правок);
3. экраны по одному: вход → лобби → профиль → лидеры → история;
4. поле последним, с переносом анимаций;
5. старый `app.js` удаляем, когда последний экран переехал.

Если решим **не** переходить на React, то вместо шага 2–5 доделываем начатое
разрезание `app.js` на ES-модули (`core/`, `game/`, `ui/`) — это вечер работы и
проект сразу становится читаемым для второго человека.

## 4. Бэк, который не жалко переписать на Go

Писать бэкенд дважды — дорого. Если коллега всё равно будет писать на Go, стоит
обсудить, не отдать ли ему бэк сразу. Но версия на JS имеет смысл, если нужно
быстро запуститься и получить работающий образец поведения.

Чтобы переписывание было механическим, а не археологией, готовим **контракт, а не
код**. Переписывается реализация, контракт остаётся:

1. **Схема API.** `docs/api/openapi.yaml` для HTTP и `docs/api/ws.md` для сообщений
   WebSocket: имена событий, поля, коды ошибок. Go-сторона генерирует типы прямо из
   схемы.
2. **Схема состояния партии.** JSON Schema на то дерево, что сегодня лежит в
   `games.state`. По ней генерируются и типы TS, и структуры Go.
3. **Золотые тесты движка.** Каталог `fixtures/`: в каждом файле `cfg`, состояние,
   ходы обоих игроков и ожидаемое состояние после них. Текущий движок умеет
   их породить — набор снимаем с реальных партий. Go-движок считается готовым,
   когда проходит тот же набор. Это главный артефакт: правила у нас нетривиальные
   (якоря, магнит, стены, захват пар), и словами их не передать.
4. **Миграции базы** — отдельно от кода приложения (`deploy/migrations/*.sql`,
   обычный `goose`/`dbmate`, который понимают оба языка).
5. **Слои без магии.** `transport` (HTTP/WS) → `service` (сценарии) → `store` (SQL).
   Никаких ORM-хитростей, запросы — обычный SQL. Так код читается построчно и
   переносится один в один.
6. **Конфиг только через переменные окружения**, без «умного» чтения файлов.

Стек для JS-версии, если пишем её: Node 22, Fastify, `ws`, `pg` (без ORM),
`zod` для разбора входа, `argon2` для паролей, `jose` для JWT.
Всё это имеет прямые аналоги в Go: `net/http`/`chi`, `gorilla/websocket`, `pgx`,
валидация руками, `golang.org/x/crypto/argon2`, `golang-jwt`.

Отдельно про аккаунты. Решено делать своё целиком, поэтому на бэке появляется:
регистрация с подтверждением по коду, вход, сброс пароля, хранение сессий
(короткий access-JWT + refresh в httpOnly-куке), письма через SMTP Яндекса.
Это самое неприятное место переезда — примерно неделя аккуратной работы, и ошибаться
тут нельзя. Три правила, которые снимают большую часть риска:

- пароли — только argon2id, никаких самодельных схем;
- коды подтверждения — одноразовые, с коротким сроком и счётчиком попыток;
- выход и смена пароля обязаны убивать все refresh-токены игрока.

Перенос нынешних аккаунтов из Supabase: экспортировать `auth.users` можно, но хеши
паролей оттуда к себе не переложить. Значит, при переезде всем придётся задать
пароль заново по письму «сбросьте пароль». Для текущих тестовых аккаунтов это
неважно, но если к моменту переезда появятся живые игроки — это нужно заранее
сказать им письмом.

## 5. Репозитории: два в организации

Организация на GitHub даёт общие права, секреты и Actions на всех. Репозитория два.

Организация [ghost-five](https://github.com/ghost-five): репозитории
[frontend](https://github.com/ghost-five/frontend) и
[backend](https://github.com/ghost-five/backend).

```
ghost-five/frontend                ghost-five/backend
  index.html, app.js, styles.css     src/        сервер
  engine.js   правила партии         migrations/ схема базы
  fixtures/   золотые тесты          deploy/     compose, Caddy, инструкция
  tools/      стенд и сценарии       docs/api/   openapi.yaml, ws.md, схема
  docs/architecture.md               .github/workflows
  .github/workflows
```

**Правила партии пока живут во `frontend`**: там единственная реализация и золотые
тесты к ней. Когда в `backend` появится движок на Go, фикстуры переезжают туда
вместе с ним — к реализации, а не наоборот. Фронту движок останется нужен навсегда:
игра с ботом и вдвоём на одном устройстве идёт без сервера вообще.

**Контракт живёт в `backend`** — его реализует сервер, а фронт потребляет. Фикстуры
самодостаточны (обычный JSON), поэтому Go-тесты берут их из `frontend`, пока не
переехали.

Цена двух репозиториев, о которой стоит помнить: изменение контракта — это два
коммита в двух местах и шанс разъехаться. Поэтому `docs/api` в `backend` —
единственный источник правды, а фронт тянет типы оттуда, а не пишет свои руками.
Сегодня это уже заметно: `node tools/schema-check.mjs` во `frontend` читает схему
из соседнего репозитория, поэтому их удобно держать рядом в одной папке.

## 6. Своя ВМ: что и где крутится

Минимальный разумный набор на одной машине (2 vCPU / 4 ГБ хватит с запасом):

```
caddy      TLS + статика фронта + проксирование /api и /ws
api        наш сервер
postgres   база с томом на диске
backup     cron: pg_dump → S3-совместимое хранилище
```

Всё — контейнерами, одним `docker compose`. Почему **Caddy, а не nginx**: сам
получает и продлевает сертификат Let's Encrypt, конфиг в пять строк, WebSocket
проксирует без шаманства. nginx берём, только если вы его уже хорошо знаете.

Базу можно вынести в управляемый Postgres у провайдера — дороже, но снимает с вас
бэкапы и обновления. На старте хватит контейнера + ежедневного дампа на сторону.

Домен: A-запись на IP машины, `www` — CNAME. Сертификат Caddy возьмёт сам.
Поддомен `stage.` — тот же compose с другим `.env` и другой базой.

## 7. Деплой и CI/CD

GitHub это умеет сам, ничего дополнительного на ВМ ставить не надо, кроме Docker.

Схема, которая работает и не требует обслуживания:

1. **Проверки на каждый PR**: линтер, типы, тесты движка на фикстурах, сборка фронта.
2. **Сборка образов на main**: `docker/build-push-action` собирает `web` и `api` и
   кладёт в GitHub Container Registry (ghcr.io) с тегом по хешу коммита.
3. **Деплой**: шаг по SSH на ВМ (`appleboy/ssh-action`) делает
   `docker compose pull && docker compose up -d && docker compose run --rm migrate`.
   Образы тянутся из ghcr по токену, секреты лежат в GitHub Environments.
4. **Откат** — это переключение тега на предыдущий хеш и повторный `up -d`.

Что нужно на машине: Docker с плагином compose, пользователь `deploy` в группе
`docker`, его ssh-ключ в секретах GitHub, `/opt/ghost-five/.env` с правами 600,
закрытый файрвол (наружу только 22, 80, 443; 22 — лучше по ключу и с fail2ban).

Чего не советую: watchtower (обновляет сам, когда не ждёшь) и сборку образов прямо
на ВМ (съедает процессор, который нужен игре).

## 8. Порядок работ

1. Решить развилки из раздела 3–5 (React, монорепо, что делать с аккаунтами).
2. Завести организацию и монорепо, перенести текущий код в `apps/web` как есть —
   он продолжает работать на Supabase и ничего не ломается.
3. Вынести `packages/engine` и снять `fixtures/` с реальных партий. **Это окупается
   раньше всего: без них Go-версию невозможно проверить.**
4. Описать контракт API (OpenAPI + сообщения WS).
5. Поднять ВМ, домен, compose и CI/CD на пустом бэке («здоров/не здоров») — чтобы
   деплой был готов раньше, чем появится что деплоить.
6. Бэк: аккаунты (или проверка JWT Supabase) → лобби → партия по WebSocket →
   история и рейтинг.
7. Фронт переключается на свой API экран за экраном.
8. Supabase выключаем, когда последний экран переехал.

## 9. Деньги

- ВМ 2 vCPU / 4 ГБ — примерно 400–800 ₽ в месяц у российских провайдеров.
- Домен — 200–1500 ₽ в год, в зависимости от зоны.
- Хранилище для бэкапов — десятки рублей в месяц.
- GitHub Actions на публичном репозитории бесплатны, на приватном — 2000 минут
  в месяц бесплатно, нам этого хватит с избытком.
